# Credentials

<div className="lead">
  SSH passwords, key passphrases, Git access tokens and your Native VM sign-in are each entered once
  and kept for every connection and deploy after. All of them are encrypted by the app and kept on
  this computer only.
</div>

## Encrypted on this computer

Every credential is kept in one place, on every system: `credentials.sqlite3` in the app's
[data folder](/docs/installation#where-your-data-lives), each value sealed with **AES-256-GCM**.

- **Nothing to type, nothing to allow.** Native VM encrypts and decrypts on its own. There's no master
  password, and your system's keychain isn't used at all, so macOS, Windows or Linux never asks you
  for permission.
- **Two halves make the key.** Native VM builds the key from a part built into the app and a part
  that belongs to this computer: 256 random bits in `credentials.key`, beside the database and
  readable only by you. Neither opens anything alone, so a copy of the database reveals nothing, to
  anyone.
- **A value can't be moved.** Each value is sealed with its own name, so one copied onto another
  entry fails to decrypt rather than answering for it.

**Credentials** in the Servers window says how they're kept, how many are saved, and where this
computer's half of the key is. There's nothing to choose. Every field that asks for a secret says it
will be kept encrypted on this computer.

<Callout type="note">
  The encrypted store protects against a copied database. Something that can read all of your files
  *and* has Native VM could still make the key: only a password you typed every time, or the system
  keychain, could stop that, and Native VM asks for neither by design.
</Callout>

## Updates and reinstalls keep them

Installing an update, or Native VM again, loses nothing. The app's half of the key is the same in
every version, and this computer's half stays in the data folder, which no installer or uninstaller
touches. The new app finds both and opens everything saved before it.

Each build is checked before it's released: it must open a credential an earlier build saved, or the
build fails.

<Callout type="tip" title="Backing up or moving computers">
  Keep `credentials.sqlite3` and `credentials.key` together. Without the key file, saved passwords
  and tokens can't be read, and you enter them again. A key file a restore left readable by others
  is made private again the next time Native VM reads it.
</Callout>

### Coming from an earlier version

Versions before 0.10 kept credentials in your system keychain by default. Native VM no longer reads
the keychain, so those are asked for once more, the first time each is needed, and kept encrypted
from then on.
Nothing is copied out of the keychain; you can delete Native VM's old entries there yourself.

## ssh-agent

A third way to sign in to a server, `ssh-agent`, appears only for servers that already use it: those
imported from `~/.ssh/config` without an `IdentityFile`. New servers are offered a key file or a
password.

## Key files

- **Never copied.** Native VM stores the file's path and reads it when it connects. It never holds
  key material, and no copy of your key exists anywhere but your own file.
- **The only key offered.** When you choose a key file, it's the only key tried, like OpenSSH's
  `IdentitiesOnly yes`. Otherwise a loaded agent could use up the server's sign-in attempts before
  your chosen key is ever tried.
- **Passphrases are detected.** Native VM reads the file to see whether it's protected, and only
  asks for a passphrase when it is.

## What's never done with a secret

- It's never written in plaintext, to a config file, or to the inventory of servers.
- It's never logged.
- It's never put on a command line on the server, where `ps` would show it to every user. Secrets
  travel on standard input or in the environment instead.

When something goes wrong, such as a changed value, a replaced or missing key file, or a database
that can't be read, Native VM says which in a sentence and what to do. The message never holds a
secret.

## Git access tokens

Tokens for [private repositories](/docs/apps#private-repositories) are kept the same way, one per
app, on this computer only. They're never written to the server. Removing an app with its files, or
making its code public, deletes its token.
