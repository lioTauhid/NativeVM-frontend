# Environment variables

<div className="lead">
  An app's environment lives in one file on the server, `/srv/<app>/shared/.env`, readable only by
  the app's own account. Every release uses it, and you edit it from the app's Environment tab.
</div>

## Editing the environment

Open the app and choose its **Environment** tab, or set variables in the wizard's **Configure** step
under advanced settings. On every plan, in either mode.

Saving shows a diff first. Secret-looking values stay masked, and a replaced one is marked
*(changed)*, so even a masked diff shows that a secret moved. Only the lines that changed are
touched, so the file's comments and order survive.

## After saving: restart or redeploy

A saved environment isn't in use yet. Native VM asks what the app needs:

- **Restart now** is enough for most apps: systemd reads `.env` each time the app starts.
- **Redeploy now** is recommended when the app has a build that bakes values into the files it
  makes, or when a variable with a front-end prefix changed, such as `NEXT_PUBLIC_` or `VITE_`. No
  restart changes those.
- **Later** leaves the running app as it is.

Go, .NET and Java apps only ever need a restart: none of them writes the environment into what it
builds. A stopped app isn't started for you, and an app not yet deployed uses the file on its first
deploy.

## Uploading a .env file

**Upload .env file**, beside the variables, merges a `.env` file from your computer into the app's
environment. Only its variables travel; the file, its comments and its name stay on your computer.

- It's read strictly. Values are kept exactly as written, quotes and all.
- A line that isn't `NAME=value` is skipped, and reported by its line number, never by its text,
  which could be a secret.
- A quoted value that spans several lines, such as a PEM key, is skipped whole. So is a value over
  4,096 characters, and the file can be at most 1 MB.
- **The file wins.** A variable already set keeps its place and takes the file's value; new ones go
  at the end. The note under the heading names what was added and replaced, never a value.

## Variables Native VM sets

The app's service sets a few variables itself, so the app knows where to listen. An uploaded `.env`
leaves them out, because a value in `.env` would override the service's:

| Variable | For |
|---|---|
| `PORT`, `HOST` | Apps on a port |
| `SOCKET_PATH` | Apps on a unix socket |
| `ASPNETCORE_URLS` | ASP.NET Core |
| `SERVER_PORT`, `SERVER_ADDRESS` | Spring Boot |
| `DOTNET_ROOT`, `JAVA_HOME` | .NET and Java apps on an installed runtime |

You can still set one of these by hand, and it's set as you typed it. Setting `PORT=3000` this way
would leave nginx proxying to a port your app no longer uses, so do it only on purpose.

<Callout type="tip">
  A Java app's heap follows its memory limit when one is set. To choose otherwise, set
  `JAVA_TOOL_OPTIONS=-Xmx512m` in its environment.
</Callout>

## Configuration files

Spring Boot and ASP.NET Core apps are often configured with files rather than variables. Native VM
keeps them on the server beside `.env`, in `/srv/<app>/shared/config/`, readable only by the app's
own account. Like `.env`, they belong to no release: a deploy keeps them, and a rollback runs the old
release with them.

| Framework | Files | How the app finds them |
|---|---|---|
| Spring Boot | `application.properties`, `application.yml` or `.yaml`, and a profile's `application-<profile>.*` | Spring Boot is pointed at the folder and reads it at every start, over the settings packaged in the jar. |
| ASP.NET Core | `appsettings.json`, and an environment's `appsettings.<Environment>.json` | Each file is linked into the folder the app runs from at every deploy, in place of the build's own file of that name. |

Upload them in the wizard's **Configure** step, under the environment variables in advanced
settings, with **Upload .properties or .yml** or **Upload appsettings.json**: several at once, with a
`.env` file or instead of one. Up to eight files, 1 MB each. Any other name is refused with the name
to give it, such as `application-prod.yml` for `prod.yml`.

### On the Environment tab

The app's **Environment** tab lists its files under the variables, with each one's size and the
profile or environment it's for. Each can be **viewed**, read from the server and shown read-only,
**replaced** by a file from your computer whatever it's called there, or **removed**, and more can be
uploaded. Every change is confirmed first, and the file it replaces or removes is backed up.

Spring Boot and ASP.NET Core read their files when they start, so afterwards Native VM offers a
**restart**. Removing an ASP.NET Core file offers a **redeploy** instead, which brings back the
build's own file of that name.

### What Native VM checks

- **Contents are never shown** except when you choose to view a file: not in a label, a review or a
  diff. Files are sent exactly as they are.
- **ASP.NET Core files are read as ASP.NET Core reads them**, comments and trailing commas allowed.
  A file it wouldn't start with is refused at upload, with the line.
- **Notes under the list** say when a file won't be read: a profile's file while no profile is
  active (set `SPRING_PROFILES_ACTIVE`), an environment's file for another environment than the
  app's (set `ASPNETCORE_ENVIRONMENT`), or a `.properties` file beside a `.yml` of the same name.
  They also warn about an ASP.NET Core file that sets `Kestrel:Endpoints` or `Urls`, which would
  move the app off the port nginx sends visitors to, Maven's `@…@` placeholders, and settings an
  ahead-of-time Spring build fixed when it was built.

<Callout type="tip">
  Environment variables win over every file: `shared/.env` overrides a file's value, written
  `Section__Key` for ASP.NET Core's `Section:Key`. To change a few ASP.NET Core settings, upload
  `appsettings.Production.json`: it's read over the build's `appsettings.json`, while an uploaded
  `appsettings.json` replaces the build's whole.
</Callout>
